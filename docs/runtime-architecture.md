# Runtime Architecture

NEA Project OpenVer preserves a layered compatibility model. The layers are intentionally distinct because the archived Player client is evidence and a rendering/transport consumer, not proof of a complete server implementation.

```text
Importable project package
  ?? client scripts -> Client Script Runtime
  ?? server scripts -> Server Script Runtime
                       |
                       v
                  MuDB transport
                       |
                       v
             Authoritative Game Runtime
                       |
                       v
           Preserved Player browser client
```

## Ownership

| Layer | Primary location | Responsibility |
| --- | --- | --- |
| Project package | `demo-map/`, imported packages | Maps, script manifests, and project-owned content. |
| Client Script Runtime | `demo-map/` and published client assets | Documented client-side script surface and UI/event bridge. |
| Server Script Runtime | `demo-map/src/runtime/` | Script globals, world/entity APIs, lifecycle events, and compatibility wrappers. |
| MuDB transport | `mudb/`, `local-player/`, `runtime-compat/abi/` | Recovered protocol schemas and browser/server transport evidence. |
| Authoritative Game Runtime | `local-player/backend/` plus control bridge | Player/entity state, retained replica data, and browser-facing projection. |

## Evidence Rules

An API surface may be declared before its engine behavior is recovered. The project therefore distinguishes an executable local adapter from a historical declaration and records known gaps in the generated compatibility matrix.

Use these artifacts together:

- `runtime-compat/abi/current-runtime.json` for executable ABI entries.
- `runtime-compat/abi/compatibility-matrix.json` for canonical coverage/status.
- `runtime-compat/generated/gap-report.md` for human-readable priorities.
- `runtime-compat/generated/script-corpus-gap-report.md` for real script usage pressure.
- `runtime-compat/generated/capability-gate-audit.md` for the conservative `ready` / `partial` / `blocked` launch classification of every anonymous corpus API requirement, including capability grants and executable binding evidence.

Unknown behavior stays absent or evidence-deferred; it must not be replaced with a plausible approximation and presented as native DAO3 behavior.

## Platform target

The compatibility target is the documented and locally recovered DAO3 project/runtime contract, not a selected preserved work. Captured maps are conformance corpora and import fixtures: they may prioritize missing APIs, but executable behavior must be implemented at the shared project package, Script Runtime, transport, authoritative runtime, or Player layer. Work names, private event types, private asset identities, and map-specific rules must never become runtime branches.

A project is considered playable only when its package fields, server scripts, client scripts, resources, UI, transport requirements, and authoritative state dependencies are either implemented through the shared ABI or reported as explicit unsupported capabilities before launch. Successful startup of one captured map is evidence for those exercised contracts, not completion of platform compatibility.

The project package therefore carries a generated capability manifest. It is a launch contract between the importer and runtime layers, not a replacement for either Script Runtime: it records statically visible API, module, UI, entity, player, and resource requirements, while the Runtime continues enforcing capabilities at call time. Static uncertainty is preserved as a diagnostic or block instead of silently widening the execution environment.

Captured runtime packages also carry explicit archive-relative Player runtime and bootstrap manifest paths. The package builder discovers compatible templates by manifest format and relocates them beneath the generated package identity; the backend receives those paths through environment configuration. Legacy fixed paths remain fallback defaults for the preserved standalone archive, but generated projects never require a selected work name in runtime code.

`NEA_RUNTIME_PACKAGE` is validated as a launch descriptor before any runtime layer starts. Its package identity, launcher route, decimal content ID, and relative JSON manifest paths form one consistency boundary. Missing dynamic Player runtime/bootstrap paths or traversal-shaped paths block launch; they never trigger an implicit compatibility claim based on whichever preserved archive happens to be installed.

Client capability grants for recovered packages are selected from confirmed public bindings in the current Runtime ABI. Runtime-internal script delivery is excluded, and grants are kept separate from compatibility: a granted member may still be partial when its evidence-backed behavior is incomplete. This avoids both stale under-granting and the false claim that permission implies semantic completeness.

Recovered canonical surfaces that are absent from the public declaration matrix are not automatically partial. Capability Manifest and the corpus launch audit share one evidence rule: the binding must be confirmed and executable, and it must have either direct historical-provider evidence (`player-bundle`, origin source, declaration, or protocol schema) or both a direct local implementation and direct conformance-test evidence. Script-corpus usage alone, an untested local implementation, inferred evidence, or a partial binding cannot pass this rule. A passing surface is launch-ready without being relabeled as a documented declaration.

Capability Manifest v14 also records the cross-layer flows and bound project identity a project actually requires. Client modules require the recovered `player.game-net.syncClientScriptModules` delivery flow; RemoteChannel calls require their direction-specific MuDB flow; evidenced player transform/respawn writes require the confirmed authoritative player-state bridge plus body-profile contract; and validated captured-mesh `world.createEntity()` calls require the loopback authoritative entity-projection flow. Canonical members with multiple local bindings select the adapter matching the statically inferred owner, while access mode distinguishes reads from writes and calls. RuntimeEntity `collides`, `fixed`, `gravity`, `mass`, `friction`, and `restitution` writes resolve to canonical partial requirements while the validated creation site supplies the ready projection dependency. These dependencies contribute to the same ready/partial/blocked launch decision. Property reads, unrelated player extensions, and unbound script-local entities are not mislabeled as authoritative state flow because no such equivalence exists in the contract evidence.

Server sound calls add a separate `transport:sound-playback` dependency. Capability Manifest v14 statically propagates the `Sound` return owner from `world.sound(...)` and inferred entity/player `.sound(...)` calls, so `resume`, `setCurrentTime`, `pause`, and `stop` are independently gated. Literal samples are also checked against packaged `player-block-audio` assets before launch. Dynamic samples are not assumed to exist, and browser media completion remains outside the Server Runtime contract.

An ABI entry may be `unavailable` only when direct provider evidence proves that scripts cannot access it. This differs from `declared-only`, where implementation evidence is simply absent. The selected archived Player's `UiInput.placeholderOpacity` is the first such entry: the renderable owns the state, module 21031 omits the public getter, and module 93474 hardens the constructor, preventing delivered project scripts from installing a compatible wrapper. The launch gate reports this exact blocker rather than treating the internal field as a public API.

Server terrain access is a separate capability boundary. `server.world.voxels` gates every script-facing member of the `voxels` facade and the recovered `world.size` projection at both manifest-analysis time and runtime access time. Internal physics and authoritative terrain code retain the raw `GameVoxelsRuntime`; only the Server Script Runtime global is wrapped, so terrain authorization is not conflated with entity queries or backend implementation layers.

The same facade pattern gates documented GameGUI members with `server.gui`, while unknown GUI properties remain ordinary JavaScript project state. Capability Manifest analysis builds a project-wide set of statically assigned `world.*` and `gui.*` surfaces before classifying module reads and calls. These entries are emitted as `script-owned`; they neither claim DAO3 compatibility nor block launch merely because a map uses globals as its shared state namespace.

GameStorage is isolated behind `server.storage`. The Server Script Runtime exposes a guarded facade while retaining the raw `LocalGameStorage` provider internally. Authorization and compatibility remain separate: a grant permits access, but `getGroupStorage()` remains partial because the default local provider has no evidence-backed cross-map namespace and deliberately returns `undefined` rather than aliasing it to single-map storage.

World configuration uses an attribute-level `server.world.config` boundary rather than guarding the entire shared `world` namespace. The recovered `gravity`, `airFriction`, and `fogColor` properties and the read-only `projectName` identity are protected; map-owned state remains ordinary script data. `projectName` is injected from the verified package `display.name`, and Capability Manifest v14 binds that normalized value so a manifest cannot be replayed for a differently named package. Historical `world.url` and `world.serverId` remain recovered-only because the local package and launch path do not carry authoritative DAO3 start values for them. The mutable physics/fog bindings remain partial after authorization because local value assignment is not evidence that the authoritative solver or every connected Player environment consumed the change.

Client module transport depends on package structure, not source truthiness. No declared client modules means no client-module-delivery flow. A declared module remains a transport dependency even when its UTF-8 source is empty, matching the recovered `syncClientScriptModules` dictionary contract and preventing analysis helpers from inventing a phantom `client.js` for server-only projects.

GameGUI is also transport-dependent. A project requirement carrying `server.gui` adds the `gui-command` flow over `player.gui`, covering handle-based init/show/remove/get/set commands and the return/throw/sendMessage responses proven by the protocol schema and local backend transport. Project-owned `gui.*` fields remain local JavaScript state and do not create a MuDB dependency.

Outbound server chat is modeled as a separate `chat-delivery` flow over `player.game-chat.log`. Capability Manifest analysis adds it only for calls that send text from the Server Script Runtime toward Player sessions: `world.say`, mapped entity `say`, and player-targeted private messaging. `world.onChat`, entity `onChat`, and `nextChat` are deliberately excluded because the local evidence proves their historical event shape but does not recover browser-to-server chat ingress. This keeps delivery conformance from being misreported as bidirectional chat compatibility.

Player action input is modeled as `input-event-ingress`, from the Player browser client directly to the Server Script Runtime over `player.game-net.input`. The backend accepts the recovered packet, emits a bounded structured event line, the launcher parser validates and clones it, and the Runtime reconstructs click/press/release events with the historical `ScriptShell` bitmask and dispatch order. Press/release use typed `RuntimeInputEvent` values; clicks use typed `RuntimeClickEvent` values, and both nest `RuntimeRaycastResult`. Capability Manifest analysis preserves both event owners and propagates assigned player, target, clicker, and raycast variables to their respective ABI owners. A project subscribing to those event families requires this flow at launch. Client scripts are not inserted into the path, unrelated world events do not inherit the dependency, and non-player click targets still require a validated authoritative entity binding.

Entity interaction is a separate `entity-interact-ingress` flow over `player.entity-interact`. The archived Player owns synchronized-radius target selection and sends `{ id, tick }`; the backend logs only the accepted protocol message and acknowledges it, while the launcher resolves the id through the authoritative entity map and reproduces the historical target-before-world `GameInteractEvent` dispatch. The flow does not claim interaction-component projection: `replica.interactive` is still unused locally, so Script Runtime `enableInteract` writes remain script-visible only and cannot fabricate prompts, radius checks, sounds, or targets.

Server entity queries share one recovered `ParsedSelector` implementation. It preserves string coercion, comma-union semantics, `*` / `entity`, `player`, id and tag matching, destroyed filtering, entity order, and the canonical `testSelector(selector, entity)` signature. `querySelectorAll` returns the recovered fresh mutable result array, keeping script mutations detached from the authoritative Runtime collection. It deliberately does not reinterpret whitespace as CSS intersection syntax or map `#` to display names. The global API remains partial because the historical generic `testComponent` helper is absent, but Capability Manifest may mark a concrete project requirement ready when every call is a literal composed only of the recovered tokens. Dynamic and unknown component paths remain partial.

Project launch uses a separate Capability Manifest gate before client script/UI publication, block-catalog loading, Script Runtime construction, backend spawn, or Player navigation. The gate requires the current manifest schema and binds its API version and client/server contract ids to the selected `dao3.project.json.engine`; a compatibility result cannot be replayed against another Runtime contract. Manifest v14 binds every analyzed server/client module by side, synchronized name, byte length, and SHA-256, binds the exact capability grants that affected requirement resolution, binds the validated client UI state through a canonical JSON digest, binds normalized asset file identities plus project entity `id/kind/mesh` projection evidence, binds the launch-verified storage `groupId` scope and normalized `projectName` identity, and binds the semantic contents of `current-runtime.json`, `compatibility-matrix.json`, and `runtime-contracts.json`. The Runtime ABI digest recursively excludes volatile `generatedAt` fields but rejects semantic entry or contract changes. Runtime-package startup reconstructs those inputs from project server files, Player-archive client/UI files, the asset index, the entity snapshot, project display metadata, and the current repository ABI artifacts, then reads each asset body and verifies the index byte length and SHA-256; direct import verifies the corresponding in-memory inputs, ABI artifacts, and asset bytes before publication. Non-capability world state such as entity position remains outside this digest. The gate validates a closed state vocabulary, recomputes every summary counter, and derives status from every evidence collection instead of trusting the manifest report: requirements, module resolution, resources, UI, entities, cross-runtime dependencies, and static diagnostics. `script-owned` is accepted only in the requirement inventory. A version/contract mismatch, module-set/hash mismatch, grant-set mismatch, UI/asset/entity/project-identity digest mismatch, Runtime ABI semantic mismatch, asset-body mismatch, summary mismatch, declared/derived status mismatch, or unknown state is invalid package state; any derived blocker stops launch, while every partial item is included in the startup warning.

Player session lifecycle crosses the Player browser, authoritative runtime, and Server Script Runtime through the recovered session flow. Historical `ScriptWorldSync` and the local runtime both dispatch `GameEntityEvent { tick, entity }` for player join/leave. On MuDB disconnect, the local Runtime preserves the recovered order `world.onPlayerLeave` ? `player.onDestroy` ? `world.onEntityDestroy` and reuses one event object. Capability Manifest treats join/leave subscriptions as project-ready while continuing to gate each accessed `GamePlayerEntity` member independently; this refinement does not promote the repository-wide player ABI beyond partial, and independent engine destruction sources remain unverified.

Server persistence remains a separate Script Runtime service, not a MuDB gameplay transport. `RuntimeGameStorage` creates project-local `RuntimeDataStorage` namespaces backed by atomic file replacement, recursively enforces the declared JSONValue union without serializer coercion, and serializes set, async update, increment, remove, and destroy operations through one process-local mutation queue; this prevents same-process lost updates without claiming distributed locking. `RuntimeQueryList` models page-index cursor traversal and the recovered last-page behavior. Local list queries enforce the documented page-size cap, traverse at most five `constraintTarget` levels, warn and fall back to the stored value for invalid or missing paths, apply numeric `min`/`max`, and order same-type scalar targets. Capability analysis propagates both returned object types. Every member remains partial because the historical cloud database supplied quotas, distributed ticket/retry semantics, backend error mapping, cross-process consistency, exact natural/mixed-type ordering, and authoritative group scope. The default launcher blocks `getGroupStorage()` rather than inventing a team/group identifier.

Server zones remain inside the Script Runtime layer. `RuntimeGameZone` preserves the recovered callable world lifecycle (`addZone`, `removeZone`, `zones`), normalized and mutation-refreshed selector membership, `collides=false` exclusion, entity-bounds overlap testing, `{ tick, entity }` enter/leave events, and zone-owned removal. Capability analysis propagates the returned `GameZone` owner. Non-player/entity component selectors remain unsupported because the historical `testComponent` helper is not recovered. Native physics selectors and Player-side environment rendering are separate unrecovered layers, so zone force, fog, rain, snow, and sky fields remain explicit partial configuration rather than simulated success.

Captured-mesh RuntimeEntity physics, model, and nameplate properties cross the Script Runtime/authoritative-runtime boundary through the existing loopback entity transport. Initial readonly `bounds` and subsequent whole-property `collides`, `fixed`, `gravity`, `mass`, `friction`, and `restitution` values are validated and copied into authoritative `replica.body`, alongside transform state, and the rebuild patch preserves the mutable update path. `bounds` uses the recovered body-center half-extents convention already shared by historical zone tests, local raycasts, and authoritative replicas; RuntimeEntity and RuntimePlayer reads return detached copies. Whole-property `meshInvisible`, `meshScale`, `meshOrientation`, `meshOffset`, `meshColor`, `meshMetalness`, `meshEmissive`, and `meshShininess` changes update their protocol-backed `replica.model` or body-orientation fields. The bridge rejects `meshId` mutation, so a script cannot bypass validated captured-mesh binding by replacing `mesh`; `anchorOffset`, nested object mutation, and RuntimePlayer model bindings remain absent. The recovered `showEntityName` switch controls authoritative `replica.nameplate` presence while `customName`, `nameRadius`, and whole-property `nameColor` assignments update the protocol-backed text, radius, and RGB fields. These surfaces remain partial: complete native oriented-body and Player posture/nameplate/model producer coverage is unavailable, nested component mutation is not bridged, and the authoritative runtime serializes generic entity bodies to the Player but does not execute a native generic rigid-body solver.

Fluid contact detection stays in the authoritative physics layer and consumes only preserved BlockInfo fluid ids plus the current Player body AABB. The fixed-step state retains active voxel overlaps and produces enter/leave transitions; the Server Script Runtime constructs a typed `RuntimeFluidContactEvent` with the historical `tick`, `entity`, and `voxel` fields and dispatches world before entity. Capability analysis carries that event owner through inline and named world/entity handlers. Active `fluidContacts` use a documented local AABB-overlap fraction. Native fluid forces and the historical producer's exact volume calculation remain unimplemented rather than being inferred from visual block metadata.

Solid voxel contact production crosses from the local fixed-step physics layer into the Server Script Runtime as a typed `RuntimeVoxelContactEvent`. Its eight canonical fields and world-before-entity dispatch are backed by the recovered ScriptShell and declarations. Capability analysis carries this event owner through inline and named handlers, while local collider diagnostics remain extensions. This adds object-ABI fidelity only and does not claim that the local sweep solver reproduces the native rigid-body engine or every GameEntity/GameVector3 behavior.

Tick event timing is owned by the Server Script Runtime clock boundary. The Runtime preserves the historical wall-clock elapsed formula and tick-delta skip predicate while keeping fixed-step physics integration separate. Because the local scheduler has no authoritative multi-tick frame source, it advances one tick per callback and does not infer skipped engine frames from host timer latency.

Raycast result ownership is preserved across the Script Runtime and launch gate. `world.raycast` constructs a `RuntimeRaycastResult` containing the nine fields recovered directly from the historical `GameRaycastResult` source, while the Capability Manifest propagates the result owner and the nested `hitEntity` owner. This is an object-ABI adapter only; it introduces no transport flow and does not upgrade the underlying local AABB entity intersection, RuntimeEntity/RuntimePlayer subset, or local vector representation from partial compatibility.

`world.searchBox` stays within the Server Script Runtime and introduces no transport flow. It searches the same RuntimeEntity and RuntimePlayer registry used by selectors and raycasts, using a shared axis-aligned bounds helper and the recovered body-center half-extents convention. The same helper corrects entity raycasts so `GameEntity.bounds` is not divided a second time. Native oriented-body queries and `world.useOBB` remain unavailable, so the API is partial rather than compatible.

Entity capacity is a launch-bound world configuration input rather than transport state. Source packages may provide `world.entityLimit`; otherwise import applies the recovered script-protocol identity `3400`. Capability Manifest v14 hashes the resolved value as `inputs.worldConfig`, and cold start verifies the packaged `world/world.json` value before Runtime construction. The Server Script Runtime counts only non-player entities, exposes the recovered `world.entityQuota()` formula, and makes `world.createEntity()` return `null` before lifecycle dispatch or projection when capacity is exhausted.

RuntimeEntity orientation helpers remain part of the Server Script Runtime ABI. `GameEntity.lookAt` is implemented from the recovered wrapper source rather than a replacement engine helper: it preserves the historical coercion, degeneracy handling, facing-axis matrices, gl-matrix conversion, and nonstandard component write order. Its result enters the existing whole-property `meshOrientation` projection path, so no new transport is introduced. RuntimePlayer orientation binding is still absent and the method remains partial.

`GameEntity.anchorOffset` is an explicit evidence boundary. Historical resources contain both `meshRenderBoxOffset` and `meshRigidBodyOffset`, and rigid-body position conversion consumes the latter, but no recovered source binds either value to the public property or proves sign, scaling, refresh, or write behavior. The Runtime omits the property rather than returning a synthetic zero value, and Capability Manifest analysis blocks its use with that exact evidence gap.

`GameEntity.rotateLocal` uses the same recovered orientation representation. The Script Runtime computes the meshScale-plus-orientation transform of a local pivot before and after an X/Y/Z radian rotation, normalizes the quaternion, and offsets entity position so the pivot's world position remains invariant. Both resulting whole-property writes reuse existing authoritative entity-state projection; no animation, solver impulse, or new transport behavior is synthesized. RuntimePlayer orientation remains unavailable, so compatibility stays partial.

`GameEntity.scaleLocal` shares that exact pivot-transform helper. It replaces RuntimeEntity meshScale, computes the old/new transformed pivot difference, and adjusts position to preserve the pivot's world location. The existing model-scale and transform bridges carry the resulting whole-property changes; no proportional, animated, or physics scaling behavior is invented. RuntimePlayer model scale remains unavailable, so compatibility stays partial.

Commerce events are evidence-blocked at the Capability Manifest layer. Historical `ScriptShell` consumes `tick.purchaseSuccessEvents` records containing `userId`, string `productId`, string `orderId`, and internal `messageId`; it constructs the four-field public `GamePurchaseSuccessEvent`, then acknowledges `messageId`. The archived Player `market` protocol only receives `openMarketplace` and has an empty client-to-server message surface, while `market-script` proves only open and acknowledgement calls. No recovered Player, commerce service, or backend producer forwards a purchase result into the Server Script Runtime, so projects subscribing to that event stop before launch. The generic Runtime signal remains an internal shell and is not promoted to a transport capability.

Inbound chat follows the same rule. Historical `ScriptShell` consumes `event.chatEvents.chats` records with `senderId`, `private`, and `message`, but the recovered `player.game-chat` client-to-server surface contains only administrator `noticeMessage {title,detail}`; the archived browser sender names that operation `sendGlobalNotice`. These schemas and purposes are not equivalent. Without a matching Player chat producer, `world.onChat` and `world.nextChat` remain startup blockers. The anonymous capability-gate audit consumes an explicit evidence-blocker table for chat ingress, purchase ingress, and group-storage scope so its aggregate state matches per-project launch behavior.

Damage and respawn mutation is modeled as `damage-state-projection`, from the Server Script Runtime to the authoritative game runtime and then into the recovered Player `game-net.PUBLIC.damage` / `scriptEvents.damage` surfaces. The local control bridge is authenticated and validates whether the target is exactly one bound Player session or authoritative entity id. Capability Manifest analysis requires this flow only for `hurt()`/`forceRespawn()` calls and writes to `hp`, `maxHp`, or `showHealthBar`; reads and lifecycle subscriptions remain local consumers. Script-local entities without authoritative bindings retain local events but are never assigned fabricated Player damage state.

Script-produced hurt uses a typed `RuntimeDamageEvent` and preserves the historical damaged-entity-before-world dispatch. Capability analysis carries the event owner and nested victim/attacker owners through handlers. This typed payload does not create a new ingress path: damage originating independently in the native authoritative engine remains unproven and therefore keeps the event family partial.

The associated positive-hp-to-zero transition uses a typed `RuntimeDieEvent` and preserves the same historical dying-entity-before-world dispatch. Capability analysis carries `GameDieEvent` and its nested victim/attacker owners, but the adapter remains partial because no independent native death-state producer has been recovered.

Local forced respawn uses a distinct typed `RuntimeRespawnEvent` with only `tick` and the respawned `GamePlayerEntity`, preserving the historical player-before-world dispatch. It no longer reuses the broader entity lifecycle payload or exposes a fabricated `player` alias. Automatic native respawn production remains unverified, so this adapter is partial.

Entity interaction ingress uses a typed `RuntimeInteractEvent` carrying the initiating Player and mapped authoritative target. The target receives the event before world listeners, and Capability Manifest owner propagation distinguishes `GamePlayerEntity` from `GameEntity`. This does not claim native interaction-component projection: prompts, radius selection, sounds, and browser interaction with unmapped script-local targets remain unavailable.

World tick delivery uses a typed `RuntimeTickEvent`. The ABI distinguishes the recovered `tick`, `prevTick`, `skip`, and `elapsedTimeMS` fields from the local `deltaTime` convenience extension. Historical wall-clock calculation is preserved, while the lack of authoritative multi-frame scheduler input keeps delayed catch-up behavior partial.

The Server Script Runtime represents chat payloads with a typed `RuntimeChatEvent`, but object shape and ingress are separate concerns. Historical declarations and ScriptShell prove `tick`, `entity`, `message`, and world-before-entity dispatch; the recovered local transport only proves outbound display. Capability Manifest therefore reports typed partial fields while retaining a hard startup blocker for `world.onChat` and `world.nextChat`.

Purchase success follows the same object-versus-ingress separation. `RuntimePurchaseSuccessEvent` represents the four declared fields for static ABI analysis, while recovered `market-script` open and acknowledgement directions do not prove a browser/backend producer for the Server Script Runtime event. Both purchase subscriptions remain hard startup blockers.

Keyboard input is separated from action-button input. `RuntimeKeyBoardEvent` models the declared `tick` and `keyCode`, while the historical producer requires current and previous keyboard-state arrays. The recovered local packet only carries button bitmasks, so keyboard subscriptions are requirement-level startup blockers and are not satisfied by the existing press/release transport.

Entity-to-entity collision is also separated from the local generic collider abstraction. Historical `bodyContact` and `bodySeparate` carry two entity ids, axis, and force; the current solver has no equivalent producer. Canonical contact subscriptions are therefore startup blockers, while `world.onContact` / `onContactSeparate` remain non-canonical local extensions with no adapter relationship.

The generated executable ABI references typed event objects consistently across world, entity, and player subscriptions. Structural inline payload types are retained only for explicitly local or transport-specific events without a recovered canonical object, preventing documentation from presenting two incompatible shapes for the same implemented event.

Captured dynamic entity replication is modeled separately as `runtime-entity-projection` over the authenticated `nea-control.runtime-entity` create/state/destroy operations. The launcher derives a whitelist only from `validated-mesh` resources in the accepted Capability Manifest and passes it into the Server Script Runtime. The backend then performs an independent projection-descriptor lookup before spawning the authoritative replica. Only statically identified script entities using a validated mesh add this launch dependency; unknown or dynamic mesh names remain partial and script-local, with no fabricated bounds, geometry, collision body, or backend id.

Player dialogs are modeled as `dialog-rpc`, directly from the Server Script Runtime to the Player browser client over `player.dialog`. The authenticated local control bridge supports both open-and-await-result and per-session cancel-all operations; the backend retains RPC ids, validates close results, resolves matching promises, and rejects cancelled or disconnected calls. Capability Manifest analysis adds this dependency only for `dialog()` and `cancelDialogs()` calls. The API remains partial because transport conformance does not prove every optional dialog configuration field or historical error/timing behavior.

Player wrapper creation and removal are modeled as `player-session-lifecycle`, from the Player browser client's game-net session into the Server Script Runtime. Structured backend events use a full SHA-256-derived bridge label rather than the prior readable prefix/suffix abbreviation. The parser requires that format, and backend control/session registries resolve the same label while retaining temporary compatibility for exact or legacy labels. This removes ambiguous session collisions without publishing the original session token. It still provides only a local anonymous RuntimePlayer identity, so lifecycle transport readiness does not imply complete DAO3 account/profile semantics.

Lifecycle payloads shared by player join/leave and entity create/destroy use a typed `RuntimeEntityEvent`. The two historical fields are preserved and callback ownership is propagated through world and entity handlers; `player` is retained only as a local alias. Script-created lifecycle and authenticated Player-session lifecycle are real local producers, while unrelated native engine creation or destruction remains outside the proven ingress boundary.
