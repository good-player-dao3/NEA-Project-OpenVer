# Code Quality and Maintainability

This project treats maintainability as a release gate, not an optional cleanup task.

## Scope

The maintainability limits apply to hand-written implementation code. They do not apply directly to generated ABI catalogs, archived evidence, minified bundles, cache manifests, or imported data. Those artifacts must be regenerated by their owning tool and must not become a substitute for modular source code.

## Required design checks

- One module/function should have one clear responsibility.
- Keep layers directional: interface/bridge -> application logic -> evidence/data access -> utilities.
- Extract repeated logic after the third occurrence.
- Use named constants and configuration instead of magic values.
- Validate all external input and preserve useful error causes.
- Add timeout, cancellation, and failure behavior at external boundaries.
- Prefer guard clauses and small strategy maps over deeply nested branches.
- Add focused tests for behavior and regressions.

## Large-file policy

Files over 500 lines require one of:

- a split plan with named seams and an incremental migration path;
- an explicit generated/data/evidence classification; or
- a compatibility-adapter exception documented in the task.

The first current refactor target is `Backend/local-player/backend/box3-server.cjs`. Do not rewrite it wholesale. Extract one stable seam at a time, starting with pure helpers and boundary adapters that can be tested independently.

## Reference-project detachment

External reference projects are evidence sources only. Their source trees must not define runtime architecture, public names, imports, or hard-coded paths. Rebuild the minimum required protocol/schema/physics fixtures under `Middleware/runtime-compat/evidence/`, record provenance in neutral terms, and regenerate reports from those fixtures.
